# ТАИР — API учёта тренировок

Рабочий MVP на FastAPI для подключения Flutter. PostgreSQL — основная база, SQLAlchemy 2 — работа с данными, Alembic — миграции. Docker Compose запускает PostgreSQL, миграции, API и Caddy с автоматическим HTTPS. Интерфейс Flutter в этот проект не входит.

## Что реализовано

- Вход по логину/паролю, JWT access token, ротация и отзыв refresh token. Пароли Argon2, refresh tokens хранятся в виде SHA-256 хешей. Все пользователи имеют одинаковые права; публичной регистрации нет.
- Филиалы с часовыми поясами, тренеры со ставкой зарплаты, возрастные группы.
- Карточки спортсменов, контакты родителей, несколько групп и история переводов через интервалы зачисления.
- Тарифы на 1, 4, 8, 12 занятий; ручные оплаты, купленные абонементы и защита от повторной отправки платежа.
- Недельное расписание, создание тренировок на период, перенос и отмена отдельных занятий.
- Журнал занятия, пакетная отметка присутствия, месячный табель, финансовая аналитика.
- Уведомления внутри приложения: малый остаток и долги по каждой группе.
- Исправление оплат и посещений с пересчётом, журнал изменений, архивирование справочников без удаления истории.
- Типизированная OpenAPI-схема: `/openapi.json`, Swagger UI: `/docs`, ReDoc: `/redoc`.

## Локальный запуск

Нужен Python 3.12+; текущие зависимости и Docker-образ проверяются на Python 3.14.

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.lock
pip install --no-deps -e .
export JWT_SECRET="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"
export DATABASE_URL=sqlite:///./training.db
alembic upgrade head
python -m app.cli create-user --username admin --name 'Руководитель'
uvicorn app.main:app --reload
```

Пароль первого пользователя вводится скрыто. Для работы с несколькими пользователями и параллельными запросами используйте PostgreSQL: SQLite подходит только для локального знакомства. Приложение само не создаёт таблицы при старте — всегда запускайте миграции.

## Развёртывание на VDS

Нужны Linux, Docker Engine с Compose, домен с A/AAAA-записью на сервер. Начальная конфигурация: 2 vCPU и 2 ГБ RAM; фактический размер зависит от нагрузки. Откройте входящие TCP 80/443; SSH ограничьте своими адресами. PostgreSQL и API не публикуются на внешних портах.

1. Скопируйте проект на сервер, перейдите в его папку.
2. Скопируйте `.env.example` в `.env`, задайте домен, независимые случайные `JWT_SECRET` и `POSTGRES_PASSWORD`. Пароль в `DATABASE_URL` должен совпадать с `POSTGRES_PASSWORD`; специальные символы в URL нужно кодировать. Проще использовать случайный буквенно-цифровой пароль. `.env` не хранить в Git; права файла — `chmod 600 .env`.
3. Выполните:

```sh
docker compose up -d --build
docker compose exec api python -m app.cli create-user --username admin --name 'Руководитель'
docker compose ps
docker compose logs --tail 100 api migrate proxy
```

API: `https://ваш-домен/api/v1`, документация: `https://ваш-домен/docs`. Сертификат получает Caddy; нужны доступные извне 80 и 443 и корректный DNS. API доверяет proxy headers только внутри закрытой Docker-сети, поэтому не добавляйте проброс 8000 наружу.

При обновлении сначала сделайте резервную копию, затем `docker compose up -d --build`. Миграции выполняются отдельным контейнером до старта API. Перед изменениями базы с несовместимой схемой остановите API и запланируйте окно обслуживания. Автоматического отката базы нет.

Резервная копия:

```sh
mkdir -p backups
docker compose exec -T db pg_dump -U training -d training -Fc > backups/training.dump
```

Храните зашифрованную копию вне VDS и регулярно проверяйте восстановление на отдельной базе. Восстановление в пустую подготовленную базу:

```sh
docker compose stop api
docker compose exec -T db pg_restore -U training -d training --no-owner < backups/training.dump
docker compose start api
```

Мониторинг: `/health/live`, `/health/ready`. Логи выводятся в stdout. Ограничение входа — 20 попыток за минуту на IP в одном процессе. При нескольких репликах нужен общий ограничитель на прокси/Redis. В Compose запускается один процесс API. Refresh token живёт 30 дней, access token — 30 минут. Выход отзывает refresh token; уже выданный access token действует до истечения срока.

Развёртывание следует подходу FastAPI с отдельным TLS-прокси: [контейнеры](https://fastapi.tiangolo.com/deployment/docker/), [работа за прокси](https://fastapi.tiangolo.com/advanced/behind-a-proxy/). Расчёты сериализуются блокировкой строки спортсмена внутри транзакции PostgreSQL: [SQLAlchemy FOR UPDATE](https://docs.sqlalchemy.org/en/20/core/selectable.html#sqlalchemy.sql.expression.Select.with_for_update).

## Правила расчётов MVP

Все суммы передаются **целым числом копеек**: 5500 ₽ = `550000`. Проценты задаются в basis points: 40% = `salary_bps: 4000`. `null` означает, что ставка не настроена, а не нулевую зарплату.

- В каждой категории допускается один активный тариф для всего клуба. Старые тарифы можно архивировать; цены редактируются. Оплата сохраняет свою сумму и количество занятий, изменение тарифа её не меняет.
- Оплата создаёт купленный абонемент. Остаток не сгорает и переносится между месяцами. Каждый абонемент привязан к группе; при переходе остаток автоматически в новую группу не переносится.
- Присутствие расходует самое раннее оплаченное занятие в этой группе, если дата оплаты не позже даты тренировки. При одинаковой дате порядок — время создания платежа, затем ID. Не имеет значения, в каком порядке тренер вносил отметки: расчёт идёт по датам тренировок.
- Оплата действует с начала указанной даты по местному времени филиала. Время внесения оплаты внутри дня не влияет. Будущие оплаты и отметки будущего занятия запрещены.
- Отсутствие, снятая отметка (`unmarked`) и отменённое занятие ничего не списывают. Отмена сохраняет отметки для истории; восстановление тренировки снова учитывает их.
- Если оплаченных занятий нет, посещение учитывается как долг. Денежная оценка долга фиксируется по разовому тарифу при первом создании отметки; она отдельно от оплаченной выручки и не участвует в зарплате.
- Более поздняя оплата не закрывает старый долг автоматически. В MVP нет отдельного финансового документа погашения долга. Ошибочные даты/оплаты можно исправить с причиной: подходящая оплата датой не позже занятия пересчитает распределение. Для реального погашения старых долгов отдельной операцией потребуется расширить модель, а не менять даты ради расчёта.
- Сумма оплаченных посещений считается без накопления потерь: стоимость k-го занятия = `floor(k × сумма / количество) − floor((k−1) × сумма / количество)`. Для 5500 ₽ / 12 сумма первых 8 занятий — 3666,66 ₽; все 12 дают ровно 5500 ₽. Отдельные занятия отличаются на копейку. Выбранное округление явно отличается от округления одного среднего значения.
- Отчёт разделяет поступления по дате оплаты, стоимость оплаченных посещений по дате занятия и денежную оценку долгов. Зарплата — процент от оплаченных посещений. Ставка сохраняется в тренировке при её создании; изменение ставки тренера не переписывает прошлое. При замене тренера применяется его текущая ставка.
- Зарплата округляется до копейки один раз в каждой строке «филиал + группа + тренер»; общий итог — сумма строк. Если хотя бы в одной тренировке нет ставки, соответствующая строка и общий итог зарплаты возвращают `null`.
- При фильтре по тренеру `received_kopecks` возвращает `null`: платёж привязан к группе, а занятие мог проводить другой тренер.
- Изменения посещений, платежей и тренировок пересчитывают распределение и прошлые отчёты. Закрытия финансовых периодов в MVP нет. Журнал хранит автора, причину, данные до и после исходной операции; производные перераспределения восстанавливаются из исходных записей.
- Архив доступен через `archived=true` и обычные отчёты с прошлыми датами. История не удаляется. Для корректировки посещений архивного спортсмена/группы сначала восстановите запись из архива.
- Перевод: закройте старое зачисление датой последнего включённого дня и создайте новое. Интервалы в одной группе не пересекаются; изменение зачисления не должно исключать уже сохранённые отметки. Филиал существующей группы менять нельзя — создайте новую группу.

## Основные запросы для Flutter

Все защищённые запросы: `Authorization: Bearer <access_token>`. Вход — JSON, не form-data:

```http
POST /api/v1/auth/login
Content-Type: application/json

{"username":"admin","password":"ваш пароль"}
```

При 401 обновите пару токенов через `POST /api/v1/auth/refresh` с `{"refresh_token":"..."}`. Сохраните **новый** refresh token: повторное использование старого запрещено. Выполняйте refresh последовательно, одной операцией для всех ожидающих запросов. Токены храните в защищённом хранилище устройства.

Рабочий сценарий:

1. `GET /branches`, `GET /groups?branch_id=...`.
2. `GET /trainings?starts_on=2026-11-13&ends_on=2026-11-13&group_id=...`.
3. `GET /trainings/{id}/roster` — спортсмены, отметки, остаток на дату занятия.
4. `PUT /trainings/{id}/attendance`:

```json
{
  "items": [{"athlete_id": "UUID", "status": "present"}],
  "reason": "Отметка посещаемости"
}
```

Пакет применяется целиком или отклоняется целиком. Статусы: `present`, `absent`, `unmarked`. Повторный PUT не создаёт второе посещение. Если два устройства меняют одну отметку, действует последнее успешно записанное значение; версии записей и полноценная офлайн-синхронизация пока не реализованы.

Оплата:

```json
{
  "athlete_id": "UUID",
  "group_id": "UUID",
  "tariff_id": "UUID",
  "paid_on": "2026-11-13",
  "method": "transfer",
  "request_key": "уникальный-UUID-операции"
}
```

`POST /payments`: при отсутствии `amount_kopecks` берётся цена тарифа. Один `request_key` повторно возвращает ту же оплату, другой набор данных с тем же ключом — 409. Ключ генерируется **один раз до отправки**, сохраняется до успешного ответа и используется повторно после сетевого сбоя. Для новой оплаты создаётся новый ключ. Исправление — `PATCH /payments/{id}` с суммой, датой, `voided` и обязательной причиной. Аннулирование не удаляет запись.

Карточка: `/athletes/{id}/card`. В ней последние 50 оплат и 100 отметок; вся история оплат доступна через `/payments?athlete_id=...` с пагинацией, история занятий — через табели. Баланс в карточке общий по всем группам; отдельно по группе — в журнале, табеле и уведомлениях.

Месячный табель: `/reports/timesheet?group_id=...&year=2026&month=11`.
Финансы: `/reports/finance?starts_on=2026-11-01&ends_on=2026-11-30`; фильтры `branch_id`, `group_id`, `coach_id`, `athlete_id` сочетаются.
Уведомления: `/notifications?threshold=2`.
История правок: `/audit?entity=payments&entity_id=...`.

Справочники создаются POST, читаются GET, полностью заменяются PUT с `?reason=...`. Для архивации PUT передаёт все поля и `archived: true`. Неотправленные поля PUT получают значения по умолчанию — это не PATCH.

Списки возвращают `items`, `total`, `offset`, `limit`, максимальный размер страницы — 200. Общий диапазон отчёта ограничен 366 днями, генерация расписания — 92 днями. Дни недели: понедельник = 0, воскресенье = 6. Генерация вызывается явно при открытии/подготовке периода: `POST /trainings/generate`. Она повторяема и не дублирует существующие даты/время; изменение шаблона расписания не перемещает уже созданные занятия.

Даты: `YYYY-MM-DD`, время: `HH:MM:SS` в часовом поясе филиала; служебные метки времени — UTC. Ошибки: 401 — вход/токен, 404 — запись не найдена, 409 — конфликт бизнес-правил/дубль, 422 — неверные данные, 429 — частые попытки входа. Для 409 показывайте `detail`, для 422 учитывайте массив ошибок FastAPI.

## Проверки и границы версии

```sh
pytest -q
ruff check .
ruff format --check .
```

Для отдельной временной PostgreSQL (не использует production-данные):

```sh
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from test
docker compose -f compose.test.yaml down -v
```

Этот запуск проверяет те же сценарии на PostgreSQL и дополнительно параллельные оплаты и отметки. Локально выполнены 15 тестов на SQLite (1 проверка PostgreSQL пропущена), проверен цикл миграций, сгенерирован SQL PostgreSQL и проверены обе конфигурации Compose. Через Postman CLI выполнены 4 HTTP-проверки работающего локального сервера — все успешны. Статические проверки Ruff проходят. Docker-служба в рабочем окружении не запущена: сборка контейнеров и проверка параллельных транзакций на настоящем PostgreSQL здесь не выполнялись.

Макеты Figma не удалось прочитать из-за ошибки выбора слоя и лимита подключённого тарифа. Реализация основана на полном описании MVP из связанного чата; соответствие полям конкретных экранов не проверено.

В MVP нет push/SMS, родительских кабинетов, онлайн-оплаты, Excel-экспорта, произвольного ручного изменения баланса, закрытых периодов и отдельного погашения старых долгов. Ручные корректировки выполняются через исходные оплаты и посещения. Уведомления вычисляются при запросе, без фонового сервиса. Для небольшого клуба этого достаточно; перед масштабированием стоит заменить последовательные расчёты балансов в карточках/уведомлениях на агрегирующие запросы и добавить нагрузочные проверки.

Готовая схема для импорта или генератора клиента — `openapi.json`. Коллекция быстрых проверок — `postman-smoke.json`. После запуска API:

```sh
/Users/bogdan/.local/bin/postman collection run postman-smoke.json --env-var baseUrl=http://127.0.0.1:8000 --reporters cli
```

На другой машине используйте путь к своему Postman CLI. Вход в аккаунт Postman для локальных проверок не требуется; без него CLI может вывести сообщение о невозможности публикации результатов в облако.
